# 影空首次跑動與轉場

## 已確認的原因

在既有流程中，`applyComposition` 只在場景建立後提出東向跑步請求。其他方向要到移動才呼叫 `AnimationClip.ensure`。當圖集未準備好，角色已依物理移動，畫面則繪製站姿。限速追蹤顯示受影響方向的請求發生在按方向後，首張跑步格出現在請求回應完成後。東向的較短空窗來自進場雖已請求，圖集尚未就緒便開放操作。

Phaser 在圖檔處理成功後註冊 spritesheet，WebGL 紋理來源也在該流程建立。使用的播放器可直接依編號切格。實驗確認了請求／註冊閘門缺失，未個別量測 Safari 的 CPU 解碼與 GPU 上傳時間。

## 載入與轉場

- 進場的 Phaser preload 只載所選解析度的四套跑步與四套待機。八張圖集都已註冊到末格後，才建立操作並關閉載入提示。必要圖集失敗時提供重新載入。待機視窗、遊戲存檔與 PWA 邏輯不涉及此閘門。
- 可朝未阻擋方向開始跑步格，無須等下一個 Arcade Physics 步進。後續跑步時序仍照位移，遇牆回站姿。沒有加入遊玩時輸入等待。
- 進場後另排三套已核准的施法。診斷與其他非必要圖集仍在使用時讀取。玩家主動改解析度時，操作繼續使用已備妥的一套，另一套跑步與待機都就緒後再切換。
- 跑步、待機畫格立即切換。只將等比顯示尺寸以 120 ms 平滑收斂，快速改向時由當下顯示尺寸續接。時間不影響物理、打擊或動畫相位。腳底原點維持 `(0.5,338/384)`。減少動態偏好採立即切換。東 100%、西 100%、北 114%、南 95%，待機和施法維持原尺寸。預設高度 207%，鏡頭 1.3。
- 與霧竹林 2.0 共同接點只有 `ForestScene.ts`，本次只修改載入與角色更新。環境建置和場景位置維持原設定。

## Chromium 預覽實測

使用本機正式建置、模擬 iPhone 橫向 852×393，限速設定為 400 ms 延遲、2,000,000 bytes/s 下行。每個方向重新導覽並停用 HTTP 快取。以瀏覽器 `keydown` 事件至第一個觀察到跑步圖集的動畫影格計算。這是瀏覽器內的取樣值，實體輸入、顯示器延遲與 Safari 效能仍需真機驗收。

| 方向 | 修改前事件到跑步格 | 修改後事件到跑步格 |
|---|---:|---:|
| 東 | 222 ms | 2.3 ms |
| 西 | 996 ms | 2.0 ms |
| 北 | 818 ms | 2.1 ms |
| 南 | 1,033 ms | 2.5 ms |

舊版每方向已有 162–954 ms 的可觀察位移才切換跑步。新版四向均先觀察到跑步格才觀察到位移。相同 iPhone 限速模式，冷啟動至可操作由約 3.35–3.81 秒變為 4.63–4.86 秒。模擬 iPad 橫向的另一次相同限速初始化測試，第一次約 4.52 秒，允許快取的第二次約 3.77 秒。這些是單次樣本，受本機負載及資源驗證影響。

北向 Run → Idle 的固定畫面測得圖像顯示邊長約 126.17 → 110.68 世界單位，首個待機格仍為 126.17，此後單調收斂，觀察到約 139 ms 到達端點（演算法為 120 ms，取樣受瀏覽器幀率限制）。腳底原點每次取樣均相同。模擬 iPad 搖桿也驗證 384 px 切換在新圖集就緒前保留 256 px 動作。

## 下載與記憶體

數字來自清單中的 WebP 大小，以及整張圖集寬×高×4 的 RGBA 估算。保守估計未包括 GPU 副本、資源解碼暫存及瀏覽器程序開銷。

| 解析度 | 進場八張必要動畫 | 進場動畫 RGBA | 背景施法下載／RGBA | 同解析度動畫快取 |
|---|---:|---:|---:|---:|
| 256 px | 2,518,016 B | 25.75 MiB | 1,163,582 B／12 MiB | 37.75 MiB |
| 384 px | 4,854,040 B | 57.94 MiB | 2,254,852 B／27 MiB | 84.94 MiB |

256 px 冷啟動的必要動畫、既有 14 張環境與四張站姿 WebP 合計 3,626,092 B，另計 HTML、JS、CSS。舊流程進場只暖載 175,824 B 東向跑步，並在首次待機追加 493,008 B 南向待機。新流程在進場交換較高下載量換取首次動作即時。主動切換解析度後，先前圖集仍在本頁快取，全部兩組約 122.69 MiB，另計任何診斷圖集。行動實機優先驗證預設 256 px、首次進場、連續切換、觸控與 Safari 記憶體壓力。
